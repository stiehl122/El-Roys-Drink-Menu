# Feature Ideas for El Roy's Drink Menu

**Generated:** 2026-03-19
**Current version:** v0.4.2
**Context:** Post-accessibility sprint. Supabase auth, full ARIA, CSS custom properties, footer, hex inputs all shipped. The app is solid and accessible. Time to make it *powerful*.

---

## Quick Wins

### 1. Drag-to-Reorder Items

**Problem:** Right now, items within a category have no ordering control. The order you add them is the order they display. During a busy shift, a manager might want to feature a new tap at the top.

**Approach:** Use the native HTML Drag and Drop API (no library needed). Add `draggable="true"` to `.current-item` rows in manager view. On `dragstart`/`dragover`/`drop`, reorder items in `menuState[catId].items` and re-render. CSS `opacity: 0.4` on the dragged item, a blue border on the drop target. Also add up/down arrow buttons as a keyboard-accessible fallback (similar to category reorder).

**Tradeoffs:** Touch drag-and-drop is notoriously inconsistent on mobile Safari. The arrow button fallback covers this, so the drag is a progressive enhancement.

**Time:** ~45 min.

---

### 2. "Undo Remove" Toast

**Problem:** Removing an item from the menu triggers a `confirm()` dialog, which is clunky and interrupts flow. Worse, the native dialog looks ugly and can be alarming on mobile.

**Approach:** Replace `confirm()` with a 5-second undo toast. When the user taps the delete button, immediately mark the item `onMenu: false` and re-render, but show a toast with an "UNDO" button. If the user taps undo, restore the item. If the toast expires, persist the removal. Store the undo payload in a simple `_pendingRemoval` variable.

**Tradeoffs:** Slightly more complex state, but massively better UX. The `confirm()` for category deletion (admin-level, destructive) can stay.

**Time:** ~30 min.

---

### 3. Keyboard Shortcut: Ctrl+S to Save

**Problem:** Managers editing the menu have to mouse/tap to the Save button. Power users expect Ctrl+S / Cmd+S.

**Approach:** Add a global `keydown` listener that checks for `(e.metaKey || e.ctrlKey) && e.key === 's'` when `isManagerMode` is true. Call `e.preventDefault()` and trigger `saveMenu()`. Show the save toast as confirmation.

**Tradeoffs:** None. Pure upside.

**Time:** ~10 min.

---

### 4. Relative Timestamps ("Updated 3 hours ago")

**Problem:** "Last Updated: Wed, Mar 19 at 2:30 PM" is precise but not instantly parsable. "3 hours ago" tells you freshness at a glance.

**Approach:** Write a tiny `timeAgo(ts)` function (under 20 lines) that returns "just now", "5 min ago", "2 hours ago", "yesterday", or falls back to the full date for anything older than 48h. Use it in the header `Last Updated` label and the footer. Update on a 60-second interval tied to the existing polling cycle.

**Tradeoffs:** Relative time can be confusing if the device clock is wrong. Fall back to absolute format for anything over 2 days.

**Time:** ~20 min.

---

### 5. Empty State Illustrations

**Problem:** "Nothing listed yet." is functional but dull. A fresh category with no items is a missed opportunity to guide the user.

**Approach:** Replace the text-only empty state in both public and manager views with a styled block. In manager mode: "No items yet -- start typing below to add one" with a subtle downward arrow or pulse animation on the input. In public view: "Check back soon!" with the category icon enlarged and faded. Pure CSS, no images needed.

**Tradeoffs:** Minimal. Just CSS and a few `innerHTML` tweaks.

**Time:** ~20 min.

---

### 6. Shake-to-86 Visual Feedback

**Problem:** When you 86 an item, the only feedback is a toast message. The moment should feel decisive -- this is a high-emotion action in a busy bar.

**Approach:** Add a CSS `@keyframes shake` animation (quick horizontal jitter, 300ms). When `toggle86()` sets `eightySixed = true`, briefly apply a `.shake` class to the item row before re-rendering. Pair it with a brief red flash on the item's background. Restoring an item gets a subtle green pulse.

**Tradeoffs:** Purely cosmetic, but it makes the interface feel alive and gives immediate visual confirmation that something happened.

**Time:** ~15 min.

---

### 7. Long-Press / Right-Click Context Menu on Items

**Problem:** Each item in the manager view has 4-5 tiny action buttons (desc, recipe, 86, delete). On mobile, these are cramped. On desktop, right-click does nothing.

**Approach:** Add a `contextmenu` event listener (desktop) and a long-press handler (touch: `touchstart` timer + `touchend` cancel, ~500ms threshold) that opens a simple absolutely-positioned div with the same actions as larger, tap-friendly buttons. Close on outside click or Escape.

**Tradeoffs:** Slightly complex touch handling. Keep the inline buttons too -- the context menu is additive, not a replacement.

**Time:** ~40 min.

## Solid Features

### 8. Price Field

**Problem:** The menu has no prices. For a bar that wants to show pricing on their public menu, this is a gap. Even bars that don't show prices publicly might want to track them internally for staff reference.

**Approach:** Add an optional `price` field to each item (stored as a string, not a number, to handle "$5", "market", "8/12" for half/full). In the manager view, add a small inline input next to each item name (width: 70px, placeholder "$"). In the public view, render the price right-aligned on the same line as the item name. Add an admin-level toggle: "Show prices on public menu" (stored in `_config`). When off, prices are still editable in manager mode but hidden from the public view.

**Tradeoffs:** Adds a field to every item. Existing data won't have it, but that's fine -- treat missing `price` as empty string. GroupMe messages could optionally include prices.

**Time:** ~2 hours.

---

### 9. Happy Hour / Time-Based Category Visibility

**Problem:** El Roy's likely has different offerings at different times -- happy hour specials, late-night menu, brunch cocktails. Right now, the only way to handle this is manually adding/removing items.

**Approach:** Add optional `visibleFrom` and `visibleUntil` fields to each category definition (24h time strings, e.g., "16:00" and "19:00"). In `renderPublicView()`, check the current time against these windows. Categories outside their window get hidden (or collapsed with a "Available 4-7 PM" badge). Manager view always shows everything. Store the schedule in `_config.categories`. Add simple time inputs in the Categories tab editor.

**Tradeoffs:** Requires visitors' device clocks to be accurate. Edge case: what about items that span midnight? Keep it simple -- if `from > until`, treat it as an overnight window. This feature makes the menu feel dynamic without requiring manager intervention.

**Time:** ~3 hours.

### 10. Batch 86 Mode

**Problem:** When a keg blows or a delivery doesn't arrive, a manager might need to 86 three or four items at once. Currently that's four individual taps with four individual toasts.

**Approach:** Add a "Batch 86" toggle button in the manager panel that enters a selection mode. Each item gets a checkbox. The bottom of the screen shows a floating bar: "3 selected -- 86 All / Remove All / Cancel". Tap "86 All" to mark them all in one shot, generate one combined toast, and one diff entry. This could also double as a "batch restore" mode.

**Approach detail:** The floating bar is a `position: fixed; bottom: 0` div that appears only in batch mode. Uses the same `toggle86()` logic under the hood, just in a loop.

**Tradeoffs:** Adds a mode to the manager view, which means more state to track (`isBatchMode`, `selectedItems`). But for a busy bar, this could save critical seconds.

**Time:** ~2-3 hours.

### 11. Patron-Facing QR Code Generator

**Problem:** Getting customers to actually visit the menu URL requires telling them, texting them, or posting a sign. QR codes are the standard solve, but generating one usually requires a third-party tool.

**Approach:** Build a tiny QR code generator in pure JS. There are well-known algorithms for QR code generation that can be implemented in ~200 lines of vanilla JS (the algorithm is a series of matrix operations -- no library needed). Add a "QR Code" button in the Admin tab that generates a QR code for `MENU_URL`, rendered as an SVG or canvas element. Include a "Download as PNG" button using `canvas.toDataURL()`. The QR code could be styled with the bar's accent color.

**Tradeoffs:** QR code generation from scratch is non-trivial but well-documented. The alternative is using a QR code API endpoint (e.g., `https://api.qrserver.com/v1/create-qr-code/`) which is simpler but adds an external dependency. Given the zero-dependency ethos, the pure JS approach is more aligned -- but the API approach is pragmatic and could be a `<img src="">` one-liner.

**Time:** ~4 hours (pure JS) or ~30 min (external API image).

### 12. Audit Log

**Problem:** "Who changed what, and when?" There's no history. If a manager accidentally removes an item or 86's the wrong thing, there's no trail.

**Approach:** Add a `_log` array in Firebase (under `menu/_log`). Each entry: `{ ts, user, action, detail }`. Log on save, send, 86 toggle, item add/remove. Cap at 100 entries (shift off the front when over limit). Render a scrollable log panel in a new "Activity" section at the bottom of the Manager tab. Each entry shows a human-readable line: "Luke 86'd Jalapeño Blanco at 3:42 PM". Filter by action type.

**Tradeoffs:** Writes to Firebase on every action (already happening for save/persist). The log is small (100 entries * ~100 bytes = ~10KB). Could grow the Firebase reads slightly. Worth it for accountability.

**Time:** ~3-4 hours.

### 13. "Staff Favorites" or "Manager's Pick" Badge

**Problem:** Bars love featuring certain drinks. There's no way to call out a recommended item beyond the description field.

**Approach:** Add a `featured` boolean to items. In manager view, add a star toggle button next to the 86 button. In public view, featured items get a small fire/star badge and are visually elevated (subtle gold left-border or background tint using `var(--gold)`). Limit to 1-2 featured items per category (enforce in the toggle logic). GroupMe messages could note featured items.

**Tradeoffs:** Risk of every item being "featured," which defeats the purpose. The per-category limit helps. Keep the visual treatment subtle -- a heavy badge would cheapen the design.

**Time:** ~2 hours.

---

### 14. Multi-Channel Notifications (SMS / Slack / Discord)

**Problem:** GroupMe is great, but not every bar uses it. Staff might prefer Slack or Discord. Patrons might want a text.

**Approach:** Abstract the notification target. Currently `sendUpdate()` builds a message and posts to `/api/send-groupme`. Refactor to support multiple "channels" configured in Admin. Each channel has a type (`groupme`, `slack-webhook`, `discord-webhook`) and a URL/ID. Slack and Discord webhooks accept JSON POSTs with a `text` or `content` field -- trivially similar to GroupMe. Add a new Vercel API route `/api/send-notification` that accepts a channel config and message, then proxies to the right service.

**Tradeoffs:** Requires a new API route (or modifying the existing one). The message format might differ slightly per platform (Discord supports markdown, Slack supports blocks). Start with plain text everywhere and iterate.

**Time:** ~4-5 hours.

---

### 15. Dark Mode for Public View

**Problem:** The public menu is always in light mode. Bar environments are often dim. A dark public menu would be more legible and feel more on-brand for a nightlife venue.

**Approach:** The manager view already has a dark palette (`body.manager-mode` overrides). Extract the dark color values into a new `body.dark-public` class (or use `@media (prefers-color-scheme: dark)`). Add an admin toggle: "Public menu color scheme" with options Auto (follows device preference) / Light / Dark. Store in `_config.design`. The CSS custom properties architecture makes this straightforward -- just swap the variable values.

**Tradeoffs:** Need to ensure all category icon colors, badges, and text remain legible on a dark background. Test the 86'd badge, green draft dot, and description panels. This is mostly a CSS exercise.

**Time:** ~2-3 hours.

### 16. Offline-First Queue with Sync Indicator

**Problem:** If the bar's WiFi drops mid-edit, saves silently fail (the `persistState()` catch shows a toast, but changes are lost to the cloud). The localStorage fallback stores the last-read state, not pending edits.

**Approach:** When `fbWrite()` fails, stash the pending state in `localStorage` under a `hf_pending_sync` key. Show a persistent amber banner: "Offline -- changes saved locally, will sync when connection returns." Add a `navigator.onLine` listener + periodic retry (every 30s). When connectivity returns, read `hf_pending_sync`, write to Firebase, clear the key, and show a success toast. A small wifi icon in the header could indicate sync status (green dot = synced, amber = pending, red = error).

**Tradeoffs:** Conflict resolution is the hard part. If two managers edit simultaneously while one is offline, the last write wins. For a small team, this is acceptable. Document it.

**Time:** ~3-4 hours.

## Bold Bets

### 17. Live Public Menu (Firebase Realtime Listener)

**Problem:** The public menu polls every 60 seconds. If a manager 86's an item at 9:01 PM, a customer looking at the menu at 9:00:30 PM won't see the change for another 30 seconds. In a live bar, this gap matters.

**Approach:** Replace the polling mechanism with Firebase's REST streaming API (`Accept: text/event-stream` on the `.json` endpoint). This opens a persistent SSE connection that pushes changes in real-time. The browser's native `EventSource` API handles reconnection automatically. On receiving a `put` or `patch` event, update `menuState` and re-render.

**Rationale:** This is genuinely transformative for the public experience. A customer at the bar sees an item 86'd the instant the bartender marks it. No refresh, no waiting. It makes the menu feel alive. Firebase REST streaming requires no SDK -- it's just HTTP with `EventSource`.

**Implementation detail:** `new EventSource(FB_URL + '/menu.json')` gives you a stream of `{path, data}` events. On initial `put`, load the full state. On subsequent `patch` events, merge the changed paths. Fall back to polling if `EventSource` is not supported (it is, everywhere).

**Tradeoffs:** Keeps an open HTTP connection per public viewer. Firebase's free tier allows 100 simultaneous connections. For a single-location bar, this is fine. If the bar gets 100+ concurrent viewers, you'd need to upgrade the Firebase plan or add a caching layer. Consider a hybrid: stream for 5 minutes, then fall back to polling if the tab is in the background (use `document.visibilityState`).

**Time:** ~4-5 hours.

### 18. Customer-Facing "Notify Me" for 86'd Items

**Problem:** When a popular beer gets 86'd, regulars want to know when it comes back. Currently there's no way for a customer to express interest.

**Approach:** On the public menu, next to an 86'd item, show a small "Notify me" button. Tapping it opens a minimal form: just an email or phone number. Store the subscription in Firebase under `_notify/{itemId}/{email}`. When a manager un-86's an item (restores it), check `_notify/{itemId}` and send notifications. The notification could go through a new Vercel API route that sends emails (via a transactional email API like Resend -- this would be the one justified external dependency) or even just texts the manager "3 people asked about Jalapeño Blanco -- it's back!"

**Rationale:** This is a genuine competitive advantage for a bar app. No bar menu does this. It turns a negative moment (your drink is unavailable) into engagement. Even if the notification is just "tell the bartender you want Jalapeño Blanco back," it creates a feedback loop.

**Tradeoffs:** This is the first feature that would require collecting PII from customers, which introduces GDPR/privacy considerations. Keep it opt-in, don't store more than necessary, and add a way to clear the list. The email-sending capability would require an external service (Resend, SendGrid, etc.), which breaks the zero-dependency principle -- but it's a justified expansion. Alternative: skip the email and just show a counter to the manager: "4 people want this back."

**Time:** ~6-8 hours (with email), ~2 hours (counter only).

### 19. Menu Versioning / Snapshot History

**Problem:** The "Send Update" flow creates a diff against the last sent state, but there's no way to see what the menu looked like last week, or two months ago. If a manager wants to recreate a past seasonal menu, they're starting from scratch.

**Approach:** Each time "Send Update" fires successfully, snapshot the entire `menuState` (minus `_config` and `_log`) into `_snapshots/{timestamp}` in Firebase. Cap at 30 snapshots. In the Admin or Database tab, add a "History" panel showing a list of snapshots by date. Clicking one shows a read-only preview of the menu as it was at that point. Add a "Restore" button that copies a snapshot back into the active state (with a confirmation dialog).

**Rationale:** Seasonal menus are a huge deal for bars. Being able to say "load the December 2025 holiday menu" in two taps is powerful. It also functions as a backup/recovery mechanism.

**Tradeoffs:** Snapshots increase Firebase storage. 30 snapshots * ~5KB = ~150KB -- trivial. The restore flow needs to be careful about merging with the current category definitions (categories might have been added/removed since the snapshot). Handle gracefully: restore items for categories that still exist, skip items for deleted categories, show a warning.

**Time:** ~5-6 hours.

### 20. Embeddable Widget / iframe Menu

**Problem:** The bar might want to embed the live menu on their main website (e.g., a Squarespace or WordPress site) without directing people to a separate URL.

**Approach:** Add a `?embed=true` query parameter that strips the header, footer, sign-in button, and background, rendering just the category list with items in a minimal, iframe-friendly layout. Detect the parameter in `init()` and apply a `body.embed-mode` class that hides chrome. Provide an embed code snippet in the Admin tab: `<iframe src="https://el-roys-drink-menu.vercel.app?embed=true" width="100%" height="600" frameborder="0"></iframe>`. The embedded view inherits the Design & Branding colors.

**Rationale:** Most bars have a separate website. Embedding eliminates the "go to another URL" friction. The embed auto-updates via the existing polling (or streaming, if that lands). This could be the single most impactful feature for customer reach.

**Tradeoffs:** iframe styling can be tricky -- the embed needs to look good at various widths. Use `max-width: 100%` and test at 320px-600px widths. Cross-origin considerations: if the main site and menu are on different domains, cookies/localStorage won't transfer, but the public menu doesn't need auth. The live-streaming approach (Bold Bet #17) pairs perfectly with this.

**Time:** ~2-3 hours.

### 21. AI-Powered Item Descriptions

**Problem:** Writing compelling descriptions for 30+ menu items is tedious. "It's a jalapeño-pineapple tequila" isn't going to sell it. "Slow-infused with serrano chiles and fresh pineapple for a sweet heat that sneaks up on you" will.

**Approach:** Add a "Generate description" button (sparkle icon) next to the description textarea in manager mode. On click, send the item name, category, and recipe (if any) to a Vercel API route `/api/generate-desc` that calls an LLM API (OpenAI, Anthropic, etc.) with a carefully tuned prompt: "Write a one-sentence, enticing bar menu description for [item]. Tone: casual, confident, approachable. Max 20 words." The manager reviews and edits before saving.

**Rationale:** This is genuinely useful -- description writing is a real bottleneck. The AI doesn't replace the manager's voice; it gives them a starting draft. The prompt should be tuned to the bar's vibe.

**Tradeoffs:** Requires an API key for an LLM service (new env var). Adds a new API route. The feature is opt-in and gracefully degrades (button simply doesn't appear if the API route isn't configured). Cost is trivial -- a few cents per batch of descriptions. This is the one dependency that arguably earns its place.

**Time:** ~3-4 hours.

### 22. Menu Analytics Dashboard

**Problem:** What are the most popular items? How often do things get 86'd? Which categories have the most churn? There's no data beyond the current state.

**Approach:** Piggyback on the audit log (Feature #12). Aggregate log data into simple counters: times each item was added, removed, 86'd, restored. Store in `_analytics` in Firebase. Render a simple dashboard in a new "Insights" tab (admin only): top 10 most-86'd items (your problem children), most frequently added/removed items (seasonal rotation candidates), category activity heatmap (which categories change the most). Use CSS-only bar charts (colored divs with percentage widths).

**Rationale:** Data-driven menu management. If Modelo gets 86'd every Friday at 8 PM, maybe order more. If a cocktail gets added and removed repeatedly, maybe it's not pulling its weight.

**Tradeoffs:** Requires the audit log to be running first (dependency on Feature #12). Analytics from limited data can be misleading -- add a disclaimer: "Based on [N] logged events since [date]." The pure-CSS charts keep it dependency-free.

**Time:** ~5-6 hours (after audit log is in place).

### 23. Collaborative Editing Indicators

**Problem:** With Supabase auth supporting multiple managers, two people could be editing the menu simultaneously. The app has no awareness of this -- the last save wins, and the first manager's changes get silently overwritten.

**Approach:** Use a lightweight presence system. When a manager enters manager mode, write `{userId, name, timestamp}` to `_presence/{userId}` in Firebase. Set a TTL by deleting the entry after 5 minutes of inactivity (or on `exitManager()`). In the manager view header, show small avatars for other active editors: "Also editing: Sarah." If another manager saves while you have unsaved changes, show a conflict warning: "Menu was updated by Sarah. Reload to see their changes, or save to overwrite."

**Rationale:** This prevents the most frustrating multi-user scenario: losing your work. Even the simplest version (just showing who else is active) dramatically reduces confusion. Full CRDT-style conflict resolution is overkill for this scale; awareness + last-write-wins is sufficient.

**Tradeoffs:** Adds a Firebase write on entering/exiting manager mode and a periodic heartbeat. Presence data is ephemeral and small. The conflict detection requires reading from Firebase before each save, which adds latency -- but this is a worthwhile tradeoff for data integrity.

**Time:** ~5-6 hours.

## Summary by Priority

If I had to pick a "next sprint," here's what I'd build:

1. **Keyboard Shortcut: Ctrl+S** (Quick Win #3) -- 10 minutes, pure upside
2. **Undo Remove Toast** (Quick Win #2) -- 30 minutes, massive UX improvement
3. **Relative Timestamps** (Quick Win #4) -- 20 minutes, delightful polish
4. **Embeddable Widget** (Bold Bet #20) -- 2-3 hours, huge reach expansion
5. **Live Public Menu via SSE** (Bold Bet #17) -- 4-5 hours, transforms the public experience
6. **Price Field** (Solid Feature #8) -- 2 hours, fills a real gap
7. **Dark Mode for Public View** (Solid Feature #15) -- 2-3 hours, fits the bar vibe

The audit log (#12) and snapshots (#19) are infrastructure plays that pay off over months. The AI descriptions (#21) and analytics (#22) are the kind of features that make people say "wait, your *bar menu app* does that?"
